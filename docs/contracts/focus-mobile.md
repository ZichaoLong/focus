# Focus mobile containers

Document role: synchronized English peer. Canonical Chinese: `docs/contracts/focus-mobile.zh-CN.md`.

## Entry and authentication

An entry stores its name, origin, random instance ID and optional web-login mode. Only the selected instance maintains its business subscription.
Remote entries require platform-validated TLS. Local Focus authorization also accepts HTTP on phone loopback (`localhost`, `127.0.0.1`, `[::1]`). Basic credentials require HTTPS. Native Basic authentication uses a dedicated script-disabled top-level GET of
`/focus-connect.txt`. Subresources and redirects cannot solicit stored credentials. The exact origin and Basic challenge realm
must match. The engine owns subsequent HTTP and WebSocket Upgrade authentication within that protection space.
A rejected credential requires user correction. A timeout preserves credentials. This version supports a site-wide Basic
protection space. The entry can be reverified when the live page encounters a challenge. Focus cookies, registration,
trusted proxy proof and mutation admission follow the external-access and wire contracts.

## Host protocol v1

The `focusApp` URL query asks the root page to wait briefly for negotiation. The host checks its exact top-level origin,
root path and `meta[name=focus-mobile-contract][content="1"]`. It installs a per-document random ticket, instance ID,
protocol version and feature list and dispatches `focus-host-ready`. Unknown versions and missing offers use browser defaults.

- `wake` accepts `focus-host-resume` and `focus-host-pause`. Foreground uses the transport wake check. Background flushes text and reading coordinates.
- `thread` accepts the last thread hint from the root document using the ticket-bound `thread` operation (up to 256 characters, empty for a workspace). The shell encodes it into the next root URL. Web must confirm that target through existing server navigation.
- `resume` identifies a single recoverable window per instance. Web persists client hints, GET locators, existing writer-bound recovery records,
  the last confirmed thread, text drafts and the reading mode and position of recently confirmed threads. Each new document registers. Unsent text and verifiable reading anchors use the instance and confirmed thread or workspace.
  Attachments, approvals and send scopes still require the acknowledged writer.
  When available, strict IndexedDB transactions persist text drafts, mode and reading bookmarks for each negotiated instance. Existing Web Storage entries migrate on first use. Draft removal and retention expiry also remove the durable copy.
- `tabs` can include a display `name`. The ticket-bound `instances` operation opens the picker. `chrome(web|native)` signals whether Web exposes the picker. The destination page initially occupies the available space. If the page still lacks a picker after a short wait, the host shows a compact Switch instance action. A host connection or authentication error, or `chrome(native)`, shows the action immediately. `chrome(web)` cancels the wait and hides the action.
  On switch the host calls `__focusSetTabActive(false)` on the top document. Web checkpoints drafts and reading position, closes the socket, and pauses polling and retries. A `true` acknowledgement allows one document per instance to stay in memory. Manage instances sets a limit of 1–5 recent pages including the current page, with a default of 2. Exceeding or lowering the limit releases the least recently selected pages first. Selection calls `__focusSetTabActive(true)` and uses the existing handshake and server reread. Missing acknowledgement, memory pressure and explicit reconnect allow a cold rebuild.
- `save` uses `prompt("focus/1/<ticket>/<op>", value)` to await a native picker or write.
  `choose` accepts a filename. The user chooses the destination. `write` acknowledges Base64 chunks of at most 24 KiB of bytes.
  `finish` copies the staged file to the selected destination. `abort` releases staging. Success returns `ok`.
  Cancellation or failure stops the write. Existing authenticated Web reads supply the contents. HTML uploads use the system picker and the existing Web uploader.
- `print` accepts a ticket-bound print request with a job name up to 255 characters. Web lays out the prepared, complete Q&A preview. The shell passes the current WebView to the system print service. Android reports success only when the system returns a print job. If creation fails, the preview shows an error and keeps the content available for retry. The content stays in document memory.
- `navigation` lets the negotiated top document forward activated cross-origin HTTPS content links to the ticket-bound `external` operation. The host validates the URL, rejects embedded credentials and opens an on-demand guest view above the source page. It displays the current origin and offers the system browser. Android uses a separate process and data directory, ArkWeb a private browsing context. Guest pages receive no Focus bridge, instance credentials or instance browsing data. One system Back closes the entire guest view. Entry sign-in redirects use the instance WebView under its SSO policy.
- System UI, native drawers and the guest view handle Back first. At the active Focus root, the host checks the document ticket and calls `__focusBack()`. Web reports synchronously whether it handled one layer. File previews reuse previous-file navigation and cancellation, closing the first file to the conversation. At the conversation root, the first Back opens the local instance drawer. A second Back within two seconds of opening it backgrounds the app with the selected instance. A later Back closes the drawer. Back always closes a manually opened drawer. Leaving the foreground clears the two-second window. Older documents use WebView history first, then follow the same root Back behavior. Replaced documents, inactive tabs and uncertain asynchronous replies cannot cause a second Back. Ordinary browsers use their own navigation.
- On Android, dragging horizontally from inside the panel toward its screen edge moves the drawer with the finger. Releasing after dragging one third of the panel width or flinging toward the edge closes the drawer. A short, slow drag springs back. The list scrolls vertically, and a horizontal drag cancels the pressed row's click. Tapping the scrim outside the panel also closes the drawer immediately. Both ways of dismissing return to the current conversation even within the two-second window for a second system Back.

Top-level navigation and teardown revoke the ticket. Parking suspends its use until the same document is selected again. External documents and sandboxed HTML previews receive no bridge.
Guest URLs only open in the separate browsing context. The protocol accepts no arbitrary authenticated requests, paths, scripts or business retries. Push registration and notification permissions require separate capabilities.

## Instance drawer and Android distribution

Return to conversation and system Back in the manager select the originating instance again. Renaming preserves its retained document. Deleting or replacing its origin leaves the instance list available.

A host offering `drawer` accepts a light/dark hint with `instances` and overlays its local registry. Opening, dismissing or selecting the current entry leaves the document active. Selecting a different instance parks it with acknowledgement. Normal and reading headers expose their own trigger. The Web receives the selected name only. The native Switch instance action opens the same drawer.

An Android host offers `android-update`. About Focus Mobile dispatches the cancelable `focus-host-about` event. The trusted document uses its ticket for `apk-info` (installed version and digest), `apk-begin` (selected manifest), `apk-write` (at most 24 KiB per chunk), and `apk-finish`. The host checks the complete hash, package, version and certificate or signing lineage, then asks the user to launch the system installer. `apk-abort` and navigation discard partial files. The alternative `apk-save` verifies the same completed APK and copies it to a user-selected system document for manual installation.

An explicit Android publication writes `channels/{main|stable}.json` and `android/<sha256>.apk` in one commit on the distribution repository's main branch. Fields are package, version, version_code, source_revision (40 hex), sha256, certificate_sha256 and size (up to 32 MiB). The APK embeds the source revision. The publisher checks the expected identity and reads back and verifies bytes and signer from a new object database. Stable may promote an existing APK. Ordinary source integration and server stable Releases are independent. Direct installs permit equal version codes; channel switches need installer support and compatible application data.

An instance reads `FOCUS_MOBILE_DIST_URL` (HTTPS or SSH Git URL), defaulting to `https://github.com/ZichaoLong/focus-mobile-dist.git`. Authenticated, CSRF- and document-protected `POST /api/mobile/android/{channel}/check` accepts an empty object and returns release, checked_at and stale. An unpublished channel has a null release. Network failure marks a cached release stale; invalid artifacts never replace the channel. Source-specific durable files live under mobile-updates in the Focus data root, outside server install operations. Authenticated `GET /api/mobile/android/apk/{digest}` serves exact cached bytes. Phones contact their instance and grant the installer temporary read access only to a verified APK. Signing keys stay with the publisher.

## Managing server updates across entries

Manage instances → Server updates opens a bundled local dashboard. Each request uses a short-lived `/focus-update.html` document in the entry's own Web profile. It registers with a separate client hint, calls same-origin update endpoints and is released after the call. It has no native bridge or conversation WebSocket. Only the restricted probe can answer matching saved Basic challenges. Login and reauthorization take place in the individual entry. Older servers can upgrade from their instance settings.

Check and prepare all reads installation IDs from every entry. Check and prepare selected reads only entries marked for checking, including entries that have never been checked or whose last check failed. Both actions group aliases by installation ID and query the selected channel once per selected installation. The update checkboxes on ready installations are independent of the check selection. On confirmation, the app submits the exact ready operation IDs for the installations marked for update in sequence.

An unavailable installation retains its record and other installations can proceed. Submitted work continues on the server when the app leaves the foreground or exits. Reopening only verifies recorded operations. Unsubmitted work needs fresh confirmation. Removing an entry or changing its address clears its local record. ## On-device offline records

Android and ArkWeb negotiate `records-v1`. Saving is opt-in per entry under Manage instances → Offline records. Only the selected thread of the foreground instance is filled back to its beginning. Ordinary browsers keep their existing transcript and reading preferences.

The compact v1 GET on `/api/threads/{thread_id}/mobile-records` uses the existing authenticated document, selected-thread and backend-generation inspection fence. It projects user and assistant text, plus transient tool markers and semantic boundaries. The app's private SQLite store groups adjacent tools across pages and persists only a version, turn, first and last stable item IDs, count and ordered SHA-256 membership chain. Visible reasoning separates runs, empty assistant targets do not. Expansion verifies the original prefix, even if more items were appended. Tool headers and explicitly requested full details live in memory.

Storage is keyed by local entry UUID, exact origin, a non-authorizing session equality proof, and thread. Renewal preserves the proof. Registration under a newly issued session cannot unlock an older session's records using a shared proxy label. Confirmed authentication challenges lock content. Confirmed revocation, different proof, entry removal and address changes clear the corresponding copy. Successful manual Basic login without a matching saved origin, realm and username, or a cross-origin sign-in followed by Focus authorization, starts a fresh local copy. A disconnected device relies on the last confirmed authorization.

Both shells execute the same fixed, parameter-bound transactions. A staged historical edition becomes complete only on contiguous coverage back to the beginning under the same server observation and verified head. Recovery can use a stable item under the same observation. Upstream cursors are transient. Previously completed text stays available while a new edition builds. Partial assistant text is marked. Limits are 16 MiB per thread edition, 64 MiB per entry and 192 MiB across entries, including staged editions, plus database overhead. Thread counts are bounded at 1000 per entry and 5000 per device.

Android persists accepted conversation windows asynchronously within the same entry, authorization, storage budget and cleanup boundary. Opening a saved thread reads the page around its reading position first. On cold start, the packaged chat component reads locally while the entry connects. The live transcript takes over for the same thread and merges server items by epoch, revision and identity. Paging uses available local rows and bridges missing history with fresh online bounds from a stable item. Accepted writes may finish after navigation. Cleanup, lock and authorization changes invalidate old writes. Unvisited threads are fetched on first selection.

Android 1.11 negotiates `conversation-layout` with the instance Web client. The packaged first screen and live page share conversation controls, transcript layout and fonts. Normal mode reserves space for the composer. Reading mode hides it. The local surface is read-only. The live page restores the draft and editing when it takes over. The app remembers theme, accent, font size and language per entry. The saved thread owns its layout metadata and cleanup removes it with the copy. Older copies can open with the default layout and acquire their layout on the next online visit.

The phone header delays the connecting indicator and shows when the device is offline or the instance is unreachable. Tapping the conversation title opens the saved thread list and the offline reader action. The packaged chat stays visible during scrolling and while the switcher is open. Once painted, the online page takes over at the last message, paragraph and viewport offset, or follows new arrivals if the reader was at the tail.

Foreground backfill can reuse the ordinary Android transcript head and its server observation and continues verification and older page reads at lower priority. Readable history, durable coverage and network catch-up progress independently. Retained pages resume in place. A target without a local page can show loading and retry. ArkWeb waits for its target document on cold open. An unreachable entry also offers an explicit offline reader. Opening the reader restores its local anchor. The online page keeps reconnecting and the user can return to it manually. Explicit tool expansion waits for connection and verifies membership in place. Selecting a different saved thread for expansion may use the existing read for an already-open thread. Closed threads and unresolved operations remain subject to normal selection and recovery. Unsupported source formats retain their online presentation.

Cleanup starts from the device index and groups candidates by entry and collapsible category. Confirmed deletion, verified absence and archived threads start expanded and selected. Closed, unread for 30 days, unknown and ambiguous older records start collapsed and unchecked. The current reader requires a deliberate selection in the all-records view. Folding preserves selection. Headers show the selected count, total count and size. Locked entries show a single unchecked group.

Only the cleanup view checks metadata in the entry's own authorized profile. The server reads batches of up to 32 local thread ids under the same session scope and returns presence, archive, absence or unknown. Missing open-list entries, network failures, older servers and unavailable authorization leave deletion unconfirmed. Confirmation rechecks online archive and absence observations and retains changed or unverifiable copies.

Operators can select individual rows or the whole list across folded groups. Confirmation shows the selected count and size and identifies any selected current reader. Each entry rechecks the selected copies, lifecycle flags, reading state and authorization in a local transaction and skips changed records. Cleanup removes local titles, index, editions and anchors, invalidates pending writes and suppresses automatic re-enrollment until deliberate selection or saving. Turning off saving leaves existing records readable. Server history, login, drafts and mutation evidence keep their existing owners.
